# Two-Stage Evacuation Router

避難経路は、最初に安全そうに見えた道路で終わってよいものではありません。このプロジェクトは、まず危険区域を出て、それから条件を満たす避難所に到達する最短の有効な経路を求め、受け入れた出口と避難所、退けた出口と避難所のすべてについて理由を説明します。

技術文書の本体は英語の [README.md](README.md) です。この文書は要点だけをまとめたものですので、詳細はリンク先をご覧ください。

## 動かしてみる

Python 3.11以降に対応しています。経路探索の中核に実行時の依存はなく、中核もCLIもネットワークに接続しません。

```bash
python -m pip install -e .
evacuation-route plan examples/synthetic_city.json
```

例に使う合成都市は、**最も近い出口が経路全体としては悪い選択になる**ように作ってあります。近いほうの出口は第1段階では2で済みますが、合計は13になります。CLIはそれを代替案として報告し、他の避難所については閉鎖中なのか、危険区域の中なのか、到達できないのかを説明します。`--format json` を付けると、安定した機械可読の出力になります。終了コードは、経路がある場合が `0`、有効な経路がない場合が `2`、入力が不正な場合が `3` です。

当時のシステムは経路計算をWebサービスで行い、Androidをその上の殻として使っていました。`api` エクストラはその境界を、クライアントではなくサービスの側で再現します。CLIとHTTPは一つのシリアライザを共有していて、両者の出力が同一であることをテストで固定していますので、二つの経路が食い違うことはありません。

## 経路探索のモデル

中核は、正の重みを持つ無向の道路グラフ、出発点、避難所の候補、そして危険区域のポリゴンか危険なノードの識別子（またはその両方）を受け取ります。

1. ポリゴンの幾何をグラフのノードに射影します。境界上の点は、安全側に倒して危険とみなします
2. 出発点が危険な場合、第1段階は危険なノードとそれに隣接する安全な出口ノードの上で Dijkstra法を実行します。各経路は最初の安全なノードで終わります
3. 到達できた各出口から、第2段階は安全なノードだけの部分グラフで Dijkstra法を実行し、すべての避難所を評価します
4. **第1段階の距離と第2段階の距離の合計**が最小になる、実行可能な出口と避難所の組を選びます
5. 出発点がすでに安全な場合、第1段階は出発点における長さ0の経路になります

この目的関数は、意図的に貪欲ではありません。最も近い出口を先に選ぶと、避難所までの道のりが長くなったり、到達できなくなったりするためです。テストには反例が入っていて、経路計画の全体を単純道の全列挙と突き合わせています。

`graph.py`・`geometry.py`・`planner.py` は、ファイルを読まず、ネットワークを使わず、地図を描画せず、CLIにもサービスにも依存しません。入力の解析・HTTP・表示はアダプタです。詳しくは[アーキテクチャと不変条件](docs/architecture.md)をご覧ください。

## 制約

- ポリゴンが辺に影響するのは、その両端のノードを通じてのみです。線分とポリゴンの交差はモデル化していません
- 危険区域は和集合として扱います。危険の種類・深刻度・時間変化・混雑・収容力・不確実性はモデル化していません
- 重みは抽象的な正のコストであって、実際の歩行時間ではありません
- ノードの座標と辺の重みは独立です。座標は危険区域に入るかどうかだけを決め、距離は決めません。実際の地図データを使うなら、両方を整合させて与える必要があります
- グラフは無向で静的です。進行方向の規制や一方通行はモデルの外にあります
- 実行時の Dijkstra法の結果は安全性の形式的な保証ではありません。**この実装は実際の避難に使うためのものではありません**
